# Online Retail — продажи и повторные покупки

Я взял данные британского интернет-магазина, чтобы понять, за счёт чего менялись продажи и сколько покупателей возвращались. По товарам я разобрал кредит-ноты и посмотрел, что чаще всего покупали вместе. Я начал с очистки, потому что в одном CSV лежат продажи, отмены и служебные операции.

[Презентация (PPTX)](online-retail.pptx) · [Дашборд](dashboard/index.html) · [SQL-запросы с ответами](sql/05_questions.sql) · [Таблицы с результатами](results/)

## Данные

В датасете **541 909 строк** с 1 декабря 2010 по 9 декабря 2011 года. Одна строка — позиция в счёте. У одного счёта может быть несколько строк. Суммы в фунтах стерлингов. В основное сравнение я включил 12 полных месяцев, с декабря 2010 по ноябрь 2011. В декабре 2011 данные заканчиваются 9-го числа, и я оставил эти строки в отчёте по очистке. [Chen, D. (2015). Online Retail. UCI Machine Learning Repository, CC BY 4.0](https://archive.ics.uci.edu/dataset/352/online-retail)

## Как я очистил данные

1. Загрузил исходные поля как текст и сохранил номер строки. В следующем шаге привёл дату, количество и цену к нужным типам, очистил пробелы и привёл коды товара и счёта к верхнему регистру.
2. Нашёл **5 268 повторных копий** по всем восьми полям после нормализации. Сохранил первую строку в каждой группе. В файле нет ID позиции счёта, поэтому часть повторов могла быть настоящими строками. Если сохранить все такие товарные продажи, сумма до вычета кредит-нот вырастет на **£23 211**, примерно на **0,24%**.
3. Разделил товарные продажи и кредит-ноты. Для продажи я использовал обычный счёт с положительным количеством, для кредит-ноты — счёт с префиксом `C` и отрицательным количеством. В обеих группах цена должна быть положительной. Служебные коды вроде `POST` и `DOT` вынес отдельно. Товарный код определил по шаблону из пяти начальных цифр с необязательным буквенно-цифровым суффиксом. Добавил исключение для кода `PADS`.
4. В исходнике **135 080 строк без `CustomerID`**. Такие строки участвуют в расчёте продаж, если проходят остальные условия. На них приходится **£1,41 млн продаж** за выбранный период. Когорты и сегменты я построил по покупателям с известным ID.

После очистки по всему файлу получилось 522 507 строк продаж и 8 668 строк кредит-нот. Из них 25 099 строк пришлись на неполный декабрь 2011. В основной анализ вошло **506 076 строк**. Причину для каждой строки можно посмотреть в `retail_repeat.classified_lines`, итоги — в [cleaning.csv](results/cleaning.csv).

## Что получилось

### Продажи выросли за счёт числа заказов

За 12 полных месяцев товарные продажи составили **£9,63 млн** по **18 957 заказам**. Кредит-ноты составили **£301,8 тыс.**, или **3,13%** от продаж в деньгах. После их вычета осталось **£9,33 млн**.

С октября по ноябрь 2011 продажи выросли с **£1,10 млн до £1,45 млн**. Заказов стало 2 751 против 2 005, а средний чек снизился с £550 до £528. Я разложил изменение продаж на два вклада. Рост числа заказов добавил около **£410,5 тыс.**, снижение среднего чека уменьшило сумму на **£61,7 тыс.** Разница между месяцами составила **£348,8 тыс.** [Помесячные результаты](results/monthly_sales.csv)

Потом я проверил, какие именно заказы дали ноябрьский рост. Продажи по **заказам без ID** выросли на **£214,6 тыс.**, по **повторным** — на **£169,2 тыс.** Продажи по первым заказам снизились на **£35,0 тыс.** Доля заказов без ID в сумме продаж выросла с **9,15% до 21,73%**. Причина отсутствия ID в файле не указана. [Продажи по типу заказа](results/order_mix.csv)

### Второй заказ за 60 дней сделали 37,37% наблюдаемых покупателей

В витрине было **4 293 покупателя** с ID. У **3 613** из них наблюдались все 60 дней после первой покупки, и **1 350** сделали второй заказ в этот срок. У октябрьской и ноябрьской когорт полное окно в выбранном периоде ещё не наступило. Для них в таблице доли оставлены пустыми.

На когортной карте M1 означает покупку в следующем календарном месяце после первой. Например, у совокупности когорт, для которых M1 полностью наблюдался, в следующий месяц вернулись **932 из 3 970 покупателей (23,48%)**. Первая покупка здесь — первая видимая в файле. Особенно осторожно я сравниваю декабрь 2010 с более поздними когортами, потому что в начале файла могут появляться покупатели с более ранней историей. [Возвраты по месяцам](results/retention.csv) · [Второй заказ за 60 дней](results/second_purchase.csv)

На 1 декабря 2011 нашёл **859 покупателей**, у которых было хотя бы два заказа и больше 60 дней без покупок. Я бы проверил на этой группе гипотезу об эффективности письма с подборкой товаров. Для проверки разделил бы группу на рассылку и контроль и сравнил долю покупок за 30 дней. [Сегменты покупателей](results/customer_segments.csv)

### Лидер по кредит-нотам оказался крупной разовой операцией

У товара **23166** было **£77 480** кредит-нот. Почти вся сумма, **£77 183,60**, пришлась на один документ `C541433`. В тот же день в счёте `541431` есть продажа с тем же количеством и ценой, которая предшествовала кредит-ноте на 16 минут. Я бы сначала проверил эти два документа. Для регулярного контроля можно взять товар **22423**. У него **176 кредит-нот** на **£9 593**, или **5,70%** от суммы продаж за период. [Рейтинг товаров](results/product_priority.csv) · [Крупнейшие документы товара 23166](results/product_documents.csv)

### Какие товары покупают вместе

Я собрал список разных товаров в каждом заказе. Для анализа взял корзины с **1–50 разными товарами**. Это **16 949 из 18 957 заказов (89,41%)**, включая 1 442 корзины с одним товаром. Чтобы несколько покупок не определяли весь рейтинг, я оставил пары, которые встретились минимум в 25 заказах.

Самая частая пара — сумки **22386** и **85099B**. Они встретились вместе в **507 корзинах (2,99%)**. В **63,06%** корзин с 22386 также был 85099B. В обратном направлении доля была **36,61%**. Я бы проверил подсказку с 85099B в корзине с 22386 и измерил, изменится ли доля заказов с обоими товарами.

У лидера по lift значение **413,79**, но сама пара 23498 и 23552 встретилась всего **25 раз**. Поэтому при выборе пары для магазина я смотрел и на lift, и на число совместных заказов. [Таблица товарных пар](results/basket_pairs.csv)

## Как считаются метрики

| Метрика | Как я её считаю |
| --- | --- |
| Продажи товаров | Положительное количество × цена по строкам товарных продаж. |
| Сумма после кредит-нот | Продажи минус абсолютная сумма кредит-нот по дате оформления документов. |
| Заказы и средний чек | Одна продажа на номер счёта с товарной строкой. Средний чек — продажи / число таких счетов. |
| Доля кредит-нот | Сумма кредит-нот / продажи за тот же период. Связь кредит-ноты с номером исходного счёта в файле отсутствует. |
| Второй заказ за 60 дней | Покупатели со вторым счётом в течение 60 дней / покупатели с полными 60 днями наблюдения с момента первого счёта. |
| Удержание M0–M6 | Доля покупателей когорты, у которых есть хотя бы один заказ в календарном месяце соответствующего возраста. |
| Рейтинг для проверки | Сумма кредит-нот по товару при продажах от £1 000 и минимум пяти кредит-нотах за период. |
| Тип заказа | Первый видимый счёт покупателя, следующий счёт покупателя или счёт без однозначного ID. |
| Доля корзин с парой | Число корзин с обоими товарами / число всех корзин с 1–50 разными товарами. |
| A → B | Число корзин с A и B / число корзин с A. Для B → A в знаменателе корзины с B. |
| Lift | Доля корзин с парой / произведение долей корзин с каждым товаром по отдельности. |

## Какие приёмы SQL я использовал

- `ROW_NUMBER()` для повторных копий, порядка заказов покупателя и рейтинга товаров.
- `LAG()` для сравнения с предыдущим месяцем. Вклад числа заказов я считал по прежнему среднему чеку, а вклад чека — по текущему числу заказов.
- CTE и `generate_series()` для заполнения таблицы когорт. Месяцы за пределами периода получают `NULL`, а наблюдавшиеся месяцы без покупок — ноль.
- `GROUPING SETS` для расчёта строки по всем странам и строк для Великобритании и остальных стран одним запросом.
- Соединение списка товаров с самим собой по номеру заказа. Для каждой пары я сравнил коды товаров и оставил одну строку, чтобы не считать A–B и B–A дважды.

## Как запустить

Понадобятся PostgreSQL **16 или новее**, клиент `psql` и Python **3.10 или новее**. Готовый HTML можно открыть сразу из [dashboard/index.html](dashboard/index.html). Для пересборки скачай [официальный CSV Online Retail](https://archive.ics.uci.edu/static/public/352/data.csv) и укажи путь к нему при запуске.

В PowerShell из папки проекта, с подключением к локальному PostgreSQL:

```powershell
$env:PGHOST = 'localhost'
$env:PGUSER = 'postgres'
createdb retail_repeat
python .\scripts\build.py --source '.\retail-data\online_retail.csv'
psql -d retail_repeat -v ON_ERROR_STOP=1 -f .\sql\05_questions.sql
```

Базу достаточно создать один раз. Если `psql` недоступен в `PATH`, можно передать путь к нему через `--psql`. Если запустить скрипт без `--source`, он спросит путь через `input()`. Python копирует CSV и запускает SQL через `psql`, сохраняет выгрузки и собирает HTML. Расчёты находятся в SQL.

При сборке пересоздаются таблицы и представления проекта в схеме `retail_repeat`. Загрузка и проверки выполняются в одной транзакции. Итоги сверки находятся в [checks.csv](results/checks.csv).
